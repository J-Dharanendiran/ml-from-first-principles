# 🎛️ The Cockpit With Fifteen Knobs: Random Forest Hyperparameters, Explained

> *"Don't memorize these as a pile of Python arguments. Ask of each knob: what kind of randomness or complexity does it control?"*

---

## 🛩️ Where the Story Starts

You now understand what a Random Forest **is**: bootstrap rows, random features at every split, independent trees, aggregation.

Then you open the scikit-learn documentation and meet this:

```python
RandomForestClassifier(
    n_estimators=100, criterion="gini", max_depth=None,
    min_samples_split=2, min_samples_leaf=1, max_features="sqrt",
    max_leaf_nodes=None, min_impurity_decrease=0.0, bootstrap=True,
    oob_score=False, n_jobs=None, random_state=None, warm_start=False,
    class_weight=None, ccp_alpha=0.0, max_samples=None, ...
)
```

> 🤔 *"Which of these actually matter, what does each one do, and what happens when I turn it?"*

The way out is the same trick as everywhere in this series: **sort the knobs by what they control.**

---

## 🗂️ Three Groups of Knobs

Remember: **Random Forest = many Decision Trees + randomness + aggregation.** Each part has its own controls.

| Group | What it controls | Examples |
|---|---|---|
| **1. Forest-level knobs** | How the forest itself is built | `n_estimators`, `max_features`, `bootstrap`, `max_samples` |
| **2. Tree-level knobs** (inherited from Decision Trees) | How each individual tree grows | `criterion`, `max_depth`, `min_samples_split`, `min_samples_leaf`, `max_leaf_nodes`, `min_impurity_decrease` |
| **3. General ML knobs** | Housekeeping, speed, imbalance | `n_jobs`, `random_state`, `warm_start`, `class_weight`, `ccp_alpha` |

All the experiments below use one synthetic classification dataset (4000 rows, 20 features, 6 informative, 70/30 split), each setting averaged over 3 random seeds, so you can see real behavior and not only descriptions. They illustrate patterns on this dataset and are not universal settings.

---

# 🌲 GROUP 1: The Forest-Level Knobs

## 🔢 `n_estimators`: How Many Trees?

```
RandomForestClassifier(n_estimators=100)

Random Forest
│
├── Tree 1
├── Tree 2
├── ...
└── Tree 100
```

The default is **100**. More trees means more individual opinions to aggregate. With 5 trees voting *Apple, Apple, Orange, Apple, Orange*, the forest says **Apple** (3 vs 2).

> 🤔 *"So why not use 10,000 trees?"*

Because every extra tree costs training time, and the benefit flattens. Here is what the experiment shows:

| `n_estimators` | Test accuracy | Training time |
|---|---|---|
| 1 | 0.823 | 0.01 s |
| 5 | 0.901 | 0.04 s |
| 10 | 0.911 | 0.08 s |
| 25 | 0.918 | 0.18 s |
| 50 | 0.922 | 0.34 s |
| 100 | 0.924 | 0.70 s |
| 200 | 0.925 | 1.45 s |
| 500 | 0.925 | 3.55 s |

Read it like a story of **diminishing returns**:

```
1 → 10 trees     : accuracy jumps by 0.09
10 → 100 trees   : accuracy rises by 0.01
100 → 500 trees  : accuracy rises by ~0.001, time grows 5x
```

This is the variance formula at work. More trees only shrink the term $\frac{(1-\rho)\sigma^2}{n}$, and once that term is small, the floor $\rho\sigma^2$ dominates. Notice also that the *spread across seeds* shrank as trees grew (±0.010 at 1 tree, ±0.0007 at 500): more trees means a more stable forest, not just a slightly more accurate one.

---

## 🎲 `max_features`: How Many Features Per Split?

> **How many features does a tree consider when searching for the best split?**

Suppose the dataset has 100 features and `max_features=10`:

```
100 total features
        ↓
Randomly select
        ↓
10 candidate features
        ↓
Find the best split among those
```

This is the feature randomness from the earlier chapters. Without it, strong features dominate every tree and the trees look alike.

### Four ways to say it

| Value | Meaning | With 100 features |
|---|---|---|
| `0.5` (a fraction) | That fraction of the features | 50 |
| `10` (an integer) | Exactly that many | 10 |
| `"sqrt"` | $\sqrt{n_{\text{features}}}$ | 10 |
| `"log2"` | $\log_2(n_{\text{features}})$ | $\log_2 100\approx6.64$, which scikit-learn truncates to **6** |

I confirmed the last row on a fitted tree: with 100 features, `"sqrt"` gave 10 candidates and `"log2"` gave 6. With 20 features, `"sqrt"` gave 4 and `0.5` gave 10.

A detail worth knowing: the **default differs by task**. In my installed scikit-learn, `RandomForestClassifier` defaults to `"sqrt"`, while `RandomForestRegressor` defaults to `1.0`, meaning *all* features at every split.

### What happens when you turn it

| `max_features` (of 20) | Test accuracy |
|---|---|
| 1 | 0.880 |
| 2 | 0.909 |
| 4 (`sqrt`) | 0.924 |
| 8 | 0.926 |
| 12 | 0.925 |
| 20 (all) | 0.924 |

The trade-off from the Bagging chapters appears as a curve:

```
Very few features per split
    ↓
Trees are very diverse but each is weak   → accuracy drops (0.880 at 1 feature)

Moderate number
    ↓
Good balance                              → accuracy plateaus (0.924 to 0.926)

All features
    ↓
Trees look alike                          → no gain from extra features here
```

On this dataset, anywhere from 4 to 20 gave essentially the same result. The only clearly bad setting was starving the trees with 1 or 2 features.

---

## 🎰 `bootstrap`: Should Each Tree Get a Bootstrap Sample?

`bootstrap` decides whether trees are trained on bootstrap samples (rows drawn **with replacement**).

```
A B C D E
    ↓ with replacement
A C C E B        ← C appears twice

    ↓ without replacement
A D B E C        ← each row at most once
```

With `bootstrap=True`, each tree sees a different training set (and about 36.8% of rows are left out of each, which powers out-of-bag scoring). With `bootstrap=False`, every tree is trained on the **whole** dataset, so the only diversity left comes from random features.

| `bootstrap` | Test accuracy |
|---|---|
| `True` (default) | 0.924 |
| `False` | 0.929 |

The gap is small, about half a percentage point, and on a different dataset it could flip. The practical point: it is not a dramatic lever, and people usually leave it on, partly because `bootstrap=True` is what makes out-of-bag scoring possible.

---

## 📦 `max_samples`: How Much Data Per Tree?

When `bootstrap=True`, `max_samples` controls **how many rows each tree's bootstrap sample contains**:

```
1,000 original rows
        ↓ bootstrap sampling
500 samples (max_samples=500, or 0.5)
        ↓
Tree
```

It only works together with bootstrap: scikit-learn raises an error if you set `max_samples` while `bootstrap=False`.

| `max_samples` | Test accuracy |
|---|---|
| 0.05 | 0.861 |
| 0.1 | 0.891 |
| 0.3 | 0.911 |
| 0.5 | 0.918 |
| 0.8 | 0.924 |
| `None` (= full size) | 0.924 |

Again it is a balance:

```
Smaller sample per tree
    ↓
More randomness, more diversity
    ↓
But each tree is weaker (too small → hurts)

Larger sample per tree
    ↓
Less randomness, trees more alike
    ↓
But each tree is stronger
```

On this dataset the curve rose and flattened by 0.8, so there was no benefit from making the samples smaller. That may differ on larger or noisier datasets.

# 🌳 GROUP 2: The Tree-Level Knobs

Every tree in the forest is an ordinary Decision Tree, so you can control **how complex each tree is allowed to get**.

## 📐 `criterion`: How Is a Split Judged?

```
Candidate split → measure impurity/quality → choose a good split
```

For classification: `gini`, `entropy`, `log_loss`. For regression: `squared_error` and others. In my test the classification criteria were nearly interchangeable:

| `criterion` | Test accuracy |
|---|---|
| `gini` | 0.924 |
| `entropy` | 0.923 |
| `log_loss` | 0.923 |

(`entropy` and `log_loss` match because they compute the same quantity.)

## 📏 `max_depth`: How Deep Can a Tree Grow?

```
max_depth=3 → the tree cannot grow past level 3
```

```
Small depth → simple tree → higher bias → underfitting
Large depth → complex tree → lower bias → possible overfitting
```

| `max_depth` | Test accuracy |
|---|---|
| 1 | 0.759 |
| 2 | 0.780 |
| 3 | 0.827 |
| 5 | 0.885 |
| 10 | 0.920 |
| `None` (unlimited) | 0.924 |

Notice something distinctive about forests. For a **single** tree you would often cap depth to fight overfitting. For a forest, the deepest trees did **best** here, because averaging already handles the variance. This is the earlier lesson in action: Random Forest wants low-bias deep trees and lets aggregation cancel the variance.

## ✂️ The Other Complexity Brakes

| Knob | What it does | Example |
|---|---|---|
| `min_samples_split` | Minimum samples a node needs before it may split | `10` → a node with 8 samples stays a leaf |
| `min_samples_leaf` | Minimum samples allowed in a leaf | `5` → no leaf with fewer than 5 samples |
| `max_leaf_nodes` | Maximum number of leaves in a tree | `20` → at most 20 leaves |
| `min_impurity_decrease` | A split must improve impurity by at least this much | tiny improvements → don't split |
| `ccp_alpha` | Cost-complexity pruning strength | larger → more pruning |

Here is how much each brake simplifies the trees (100 trees, 2000-row dataset):

| Setting | Avg nodes per tree | Test accuracy |
|---|---|---|
| Defaults | 251 | 0.932 |
| `min_samples_split=50` | 73 | 0.922 |
| `max_leaf_nodes=20` | 39 | 0.920 |
| `min_impurity_decrease=0.001` | 159 | 0.932 |
| `ccp_alpha=0.002` | 111 | 0.928 |

And a sweep of `min_samples_leaf` on the 4000-row dataset:

| `min_samples_leaf` | Test accuracy |
|---|---|
| 1 | 0.924 |
| 5 | 0.920 |
| 20 | 0.904 |
| 100 | 0.845 |

The pattern: gentle brakes cost almost nothing, aggressive brakes push the trees toward high bias and accuracy falls. In a forest, these knobs are useful mostly when you want **smaller, faster, or smoother** models, not because the default overfits.

# ⚙️ GROUP 3: The General Knobs

## 🖥️ `n_jobs`: Parallel Training

Trees are independent, so they can be trained at the same time:

```
CPU
├── Core 1 → Tree
├── Core 2 → Tree
├── Core 3 → Tree
└── Core 4 → Tree
```

`n_jobs=-1` uses all available cores. (My sandbox has a single CPU, so I measured no speedup here: 21.4 s with `n_jobs=1` versus 21.1 s with `-1`. On a multi-core machine this is where the gain appears.)

## 🔁 `random_state`: Repeatable Randomness

A forest contains randomness, so repeated runs differ unless you fix the seed. On a 20-tree forest:

```
No random_state  → test accuracy: 0.9333, 0.9217, 0.9333, 0.9233   (varies)
random_state=42  → test accuracy: 0.9367, 0.9367, 0.9367, 0.9367   (identical)
```

Set it whenever you want reproducible experiments, assuming the data and pipeline stay the same.

## ➕ `warm_start`: Add Trees Without Starting Over

```
Fit 100 trees
    ↓
set n_estimators=150, warm_start=True, fit again
    ↓
Keeps the first 100, adds 50 new ones
```

I checked: after the second fit the forest had 150 trees, and the first original tree was the **same object**, kept rather than rebuilt.

## ⚖️ `class_weight`: For Imbalanced Data

```
Class A → 9,000 samples
Class B → 1,000 samples
```

`class_weight` gives the minority class more importance. I tested it on a dataset where only about 6% of rows were the minority class:

| Setup | Threshold 0.5: minority recall | Precision |
|---|---|---|
| Default | 0.443 | 1.000 |
| `class_weight="balanced"` | 0.368 | 1.000 |
| `min_samples_leaf=5` only | 0.368 | 1.000 |
| `balanced_subsample` + `min_samples_leaf=5` | **0.528** | 0.949 |

Two lessons from this run, on one dataset:

1. **`class_weight` alone did not raise minority recall** here. Fully grown trees already fit the minority rows. It helped once the trees were also restricted (`min_samples_leaf=5`): recall went from 0.368 to 0.528 compared with `min_samples_leaf=5` alone.
2. **The decision threshold was a bigger lever.** Lowering the probability threshold from 0.5 to 0.2 with default settings raised recall from 0.443 to 0.726 while precision fell from 1.000 to 0.819.

For imbalanced problems, treat `class_weight` as one tool among several (alongside threshold tuning and the right metric, such as recall or F1 and not plain accuracy). The model's accuracy was 0.967 even when it missed more than half of the minority class.

# 🌿 Random Forest Regression

Regression uses the **same structure**: trees, bootstrap, feature randomness, and aggregation by **averaging** instead of voting. The main change is the split criterion:

| Task | Criteria examples | Aggregation |
|---|---|---|
| Classification | `gini`, `entropy`, `log_loss` | Majority vote (probability average) |
| Regression | `squared_error`, `absolute_error`, `friedman_mse` | Mean of tree predictions |

In a quick regression test (1500 rows, 50 trees), the three criteria gave $R^2$ of 0.922, 0.925 and 0.922 respectively, though `absolute_error` took about three times longer to train (0.80 s versus 0.26 s).

# 🔥 The Big Picture

```
                    RANDOM FOREST
                          │
             ┌────────────┴────────────┐
       MANY DECISION TREES        RANDOMNESS
             │                         │
             │              ┌──────────┴──────────┐
             │        Random samples        Random features
             └──────────────┴─────────────────────┘
                            │
                    Individual trees
                            │
                     Aggregate output
                 ┌──────────┴──────────┐
             Classification        Regression
               Voting               Averaging
```

| Parameter | Controls | Main intuition |
|---|---|---|
| `n_estimators` | Number of trees | More averaging, diminishing returns |
| `max_features` | Candidates per split | Feature randomness: diversity vs tree strength |
| `bootstrap` | Row sampling on/off | Source of row randomness; enables OOB |
| `max_samples` | Rows per tree | Data per tree: diversity vs tree strength |
| `criterion` | Split quality measure | How splits are judged |
| `max_depth` | Tree depth | Tree complexity |
| `min_samples_split` | Samples needed to split | Prevents tiny splits |
| `min_samples_leaf` | Minimum leaf size | Prevents tiny leaves |
| `max_leaf_nodes` | Number of leaves | Caps complexity |
| `min_impurity_decrease` | Required split gain | Stops weak splits |
| `ccp_alpha` | Pruning strength | Cost-complexity pruning |
| `n_jobs` | CPU cores | Parallel training |
| `random_state` | Seed | Reproducibility |
| `warm_start` | Reuse fitted trees | Add trees incrementally |
| `class_weight` | Class importance | Imbalanced classification |

# 🧭 A Sensible Order for Tuning

This is my suggested workflow, built from the experiments above and not from a source:

1. **Start with defaults** and a fixed `random_state`. Defaults are already strong for a forest.
2. **Raise `n_estimators`** until the score stops improving (100 to 300 is where gains flattened here).
3. **Tune `max_features`**, the knob that trades diversity against tree strength.
4. **Only then** consider tree brakes (`max_depth`, `min_samples_leaf`) if you need a smaller or smoother model, and `class_weight` plus threshold tuning if classes are imbalanced.
5. Use `oob_score=True` as a free check while you experiment, and always confirm on held-out test data.

---

# 🌀 Deepest Realization

A Random Forest has many knobs, but they reduce to two questions:

```
1. How DIFFERENT are my trees?   → n_estimators, max_features, bootstrap, max_samples
2. How COMPLEX is each tree?     → max_depth, min_samples_*, max_leaf_nodes, ccp_alpha...
```

Diversity wants randomness; strength wants information. Every tuning decision is a negotiation between the two. And it all ends the same way: each tree predicts on its own, and **only then** are the predictions combined, by majority vote for classification or an average for regression.

---

# ✅ Final Takeaway

> **"A Random Forest's hyperparameters fall into three groups: forest-level knobs that set how many trees there are and how different they are, tree-level knobs that set how complex each tree can be, and general knobs for speed, reproducibility and imbalance. More trees almost always help but with diminishing returns; the interesting trade-offs are between diversity and tree strength, in `max_features` and `max_samples`, and between bias and variance in the tree brakes."**
